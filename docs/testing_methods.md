# Сравнительный анализ методов тестирования (ЛР №4)

## 1. Методы «чёрного ящика»

| Метод | Суть | Преимущества | Недостатки | Применение в проекте |
| --- | --- | --- | --- | --- |
| Эквивалентное разбиение | входные данные делятся на классы, внутри класса поведение одинаково | быстро даёт базовый набор тестов, не требует знания кода | можно пропустить дефект на стыке классов | размеры `n`, `m`: 4 класса (корректные, вне диапазона, не целые, не числа) |
| Анализ граничных значений | проверяются значения на границах классов | находит ошибки сравнений (`<` вместо `<=`) | требует знания границ | `0`, `1`, `MAX_DIM`, `MAX_DIM + 1` для размеров и столбцов |
| Анализ причинно-следственных связей | строится таблица «причина → следствие» | системно покрывает комбинации условий | таблица растёт экспоненциально | таблица условий `check_version` и `parse_request` |
| Предположение об ошибке | тестировщик предугадывает типичные ошибки | дёшево и находит «реальные» дефекты | зависит от опыта, не систематичен | `nan`/`inf`/`1e999`, минус ноль, XML/JSON-константы, рваная матрица, `10**400` |

## 2. Методы «белого ящика»

| Критерий | Что гарантирует | Стоимость | Итог в проекте |
| --- | --- | --- | --- |
| Покрытие операторов | каждая строка выполнена | низкая | покрыто 100 % |
| Покрытие решений | каждая ветка `if/else` пройдена в обе стороны | средняя | все ветки `find_zero_columns`, `format_result`, `parse_row`, `integrate` |
| Покрытие условий | каждое простое условие хотя бы раз истинно и ложно | высокая | `is_number` (3 условия), `parse_request` (5 проверок) |
| Комбинаторное покрытие условий | все комбинации условий в решении | очень высокая | `check_version` — 5 комбинаций вместо 8 (некоторые недостижимы) |

Комбинаторное покрытие быстро становится избыточным: для
`parse_request` число комбинаций условий превышает 100, поэтому
применено попарное комбинирование с явным перебором границ.

## 3. Сравнение «чёрного» и «белого» ящика

| Критерий | Чёрный ящик | Белый ящик |
| --- | --- | --- |
| Источник тестов | спецификация, ТЗ | исходный код |
| Что находит | несоответствие требованиям, ошибки на границах | непроверенные ветки, мёртвый код, необработанные исключения |
| Когда применяется | на любом этапе, в том числе без кода | после появления кода |
| В проекте | 4 дефекта из 4 найдены тестами по границам (BUG-1…BUG-4) | 100 % покрытие подтвердило отсутствие непроверенных ветвей |

Практический вывод: методы дополняют друг друга. Покрытие 100 % без
граничных значений не нашло бы ни одного из четырёх дефектов — все они
возникают на «неудобных» данных, а не в непройденных ветках.

## 4. Рекомендации по применению

1. Начинать с эквивалентного разбиения и граничных значений — это
   дешевле всего и даёт максимум дефектов на единицу усилий.
2. «Предположение об ошибке» применять к каждому внешнему вводу: пустая
   строка, `NaN`, `Infinity`, отрицательный ноль, огромные числа, разная
   длина строк.
3. «Белый ящик» использовать как контроль полноты: покрытие решений
   должно быть 100 %, покрытие условий — для решений с 2–3 условиями.
4. Комбинаторное покрытие — только для критичных решений, иначе
   стоимость тестов растёт быстрее их пользы.
5. Интеграционные тесты писать с реальным процессом, а не только с
   заглушками: заглушки не воспроизводят коды завершения и тайм-ауты.

## 5. Сравнение инструментов

| Инструмент | Плюсы | Минусы | Выбор |
| --- | --- | --- | --- |
| pytest | короткий синтаксис `assert`, параметризация, маркеры, плагины | требует установки, не входит в stdlib | выбран |
| unittest | входит в stdlib, xUnit-совместим | многословный, слабая параметризация | тесты ЛР3 сохранены как регрессия |
| coverage.py | точные отчёты, ветви, `--fail-under` | не показывает качество проверок | используется в CI |
| flake8 | быстрый, единый стиль, ловит неиспользуемые импорты | не находит логических ошибок | используется в CI |

## 6. CI/CD-платформы

| Платформа | Особенности |
| --- | --- |
| GitHub Actions | YAML-workflow в репозитории, матрица версий, артефакты, бесплатно для публичных репозиториев — используется в проекте |
| GitFlic | российская платформа, встроенный CI, реестр ПО |
| GitFlame | российский хостинг с CI и приватными репозиториями |
| Mos.Hub | платформа для госсектора, CI на базе GitLab |

Для учебного проекта GitHub Actions выбран из-за доступности и
интеграции с pull request; workflow переносится на GitFlic/Mos.Hub
практически без изменений (те же шаги: установка зависимостей, flake8,
pytest, coverage).
