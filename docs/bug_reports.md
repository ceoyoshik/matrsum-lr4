# Баг-репорты (ЛР №4)

Все дефекты выявлены при разработке тестового набора, воспроизведены
тестами и исправлены. Номера тестов соответствуют файлам в `tests/`.

---

## BUG-1. Ответ модуля обработки принимается с недопустимыми номерами столбцов

| Поле | Значение |
| --- | --- |
| ID | BUG-1 |
| Компонент | `src/protocol.py`, `parse_response` |
| Найден | при тестировании протокола (`test_parse_response_rejects_invalid_column_numbers`) |
| Тяжесть | Major |
| Приоритет | High |
| Статус | Исправлен |

**Описание.** `parse_response` проверял только тип элементов списка
`zero_columns`, но не диапазон и не уникальность номеров. Ответ с номером
`0`, отрицательным номером, номером больше `MAX_DIM` или с дубликатами
считался корректным и попадал в модуль вывода.

**Шаги воспроизведения.**

1. Сформировать сообщение `sum_response` с `zero_columns = [0]` (или
   `[-1]`, `[1001]`, `[1, 1]`).
2. Вызвать `protocol.parse_response(message)`.

**Ожидаемое поведение.** `ProtocolError`: номера столбцов нумеруются с 1 и
не повторяются.

**Фактическое поведение.** Возвращался кортеж с недопустимыми номерами,
ошибка обнаруживалась только визуально в отчёте пользователя.

**Исправление.** Добавлены проверки уникальности и диапазона
`1 .. MAX_DIM`; тесты — `test_parse_response_rejects_invalid_column_numbers`
(5 наборов).

## BUG-2. Рваная матрица вызывает `IndexError` вместо диагностики

| Поле | Значение |
| --- | --- |
| ID | BUG-2 |
| Компонент | `src/processing_module.py`, `find_zero_columns` |
| Найден | при тестировании граничных значений (`test_ragged_matrix_raises_input_data_error`) |
| Тяжесть | Major |
| Приоритет | Normal |
| Статус | Исправлен |

**Описание.** Ширина матрицы бралась по первой строке, а доступ к
элементам остальных строк не проверялся. При матрице с разным числом
элементов в строках возникал `IndexError`, не являющийся
`IntegrationError`: исключение не перехватывалось в `handle_request` и
приводило к аварийному завершению вместо сообщения об ошибке.

**Шаги воспроизведения.**

1. Вызвать `find_zero_columns([[1.0, 2.0], [3.0]])` или отправить
   `matrix_request` с `rows=2, cols=2`, `matrix=[[1,2],[3]]` напрямую в
   `handle_request`.

**Ожидаемое поведение.** `InputDataError` (или сообщение с кодом
`invalid_data` при обмене через протокол).

**Фактическое поведение.** `IndexError: list index out of range`,
трассировка в stderr, код завершения процесса 1.

**Исправление.** Перед поиском нулей проверяется прямоугольность матрицы;
тест дополнен проверкой сообщения через `handle_request`.

## BUG-3. Огромное целое число в матрице роняет обработку (`OverflowError`)

| Поле | Значение |
| --- | --- |
| ID | BUG-3 |
| Компонент | `src/protocol.py`, `is_number` |
| Найден | при тестировании классов эквивалентности (`test_is_number_huge_integer_is_not_a_number`) |
| Тяжесть | Major |
| Приоритет | High |
| Статус | Исправлен |

**Описание.** JSON не ограничивает разрядность целых, поэтому в поле
матрицы может прийти число вида `10**400`. Вызов `math.isfinite()` для
такого `int` поднимает `OverflowError`, который не перехватывался:
валидация завершалась аварийно вместо сообщения о некорректных данных.

**Шаги воспроизведения.**

1. Отправить `matrix_request` с `matrix = [[10**400]]`.
2. Вызвать `processing_module.handle_request(request)`.

**Ожидаемое поведение.** Сообщение `error` с кодом `invalid_data`.

**Фактическое поведение.** `OverflowError: int too large to convert to
float` выходит из `handle_request`, процесс завершается с трассировкой.

**Исправление.** `is_number` проверяет тип до вызова `math.isfinite` и
перехватывает `OverflowError`, возвращая `False`; добавлены тесты
`test_parse_request_huge_integer_cell` и
`test_handle_request_huge_integer_is_invalid_data`.

## BUG-4. Несериализуемое значение даёт `TypeError` вместо `ProtocolError`

| Поле | Значение |
| --- | --- |
| ID | BUG-4 |
| Компонент | `src/protocol.py`, `dump_json` |
| Найден | при тестировании записи файлов обмена (`test_dump_json_rejects_unserializable`) |
| Тяжесть | Minor |
| Приоритет | Low |
| Статус | Исправлен |

**Описание.** `dump_json` перехватывал только `ValueError` (NaN/Inf),
поэтому `TypeError` от `json.dumps` (например, множество в payload)
выходил наружу и не преобразовывался в ошибку интеграции.

**Шаги воспроизведения.**

1. Вызвать `protocol.dump_json("message.json", {"value": {1, 2}})`.

**Ожидаемое поведение.** `ProtocolError` с понятным сообщением.

**Фактическое поведение.** `TypeError: Object of type set is not JSON
serializable`; временный файл `.tmp` не создаётся, но контракт модуля
нарушен.

**Исправление.** `TypeError` добавлен в обработку рядом с `ValueError`;
тест `test_dump_json_rejects_unserializable`.
